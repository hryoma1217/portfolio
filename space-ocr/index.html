エンジン v91 での再測定

01 結論

素通し率が上がり、混入は 0 のままでした。素通しとは、読み取り結果のうち人の確認を経ずに 原価計上へ回してよいと判定したもののことです。

素通しにできた枚数（各 20 枚中）
条件 v81 v91
経路A・導入直後 2 枚 (10%) 4 枚 (20%)
経路A・使いながら覚える 5 枚 (25%) 9 枚 (45%)
経路A・定常状態 9 枚 (45%) 14 枚 (70%)
経路B・導入直後 1 枚 (5%) 1 枚 (5%)
経路B・使いながら覚える 4 枚 (20%) 5 枚 (25%)
経路B・定常状態 6 枚 (30%) 8 枚 (40%)
素通しの中の誤り 0 件

v81・v91 とも全条件で 0 件。この判定の要件は「素通しにした中に誤りを混ぜないこと」の一点なので、 そこは維持されています。削減率だけを見ると、誤りを自動で通す設計を効果ありと読み違えます。

02 確認できた API 側の変更

印字文字列を読む手段が用意された（v82 / v83）

本編 4.4 節に、こう書きました。

カンマから小数点への誤読は検算を全部通る。正規化後の数値ではなく印字文字列を見るしかない。

その「印字文字列を見る」手段が evidence.text_match と evidence.printed_text として用意されました。

経路A・文字照合の付き方（セル数）
項目 v81 v91
text_match を持つセル 0 1,372
うち false — 4
text_match が付かないセル 1,615 241

v91 で残る 241 件は、値を持たない幾何セル（表の枠、行の union）で、元から検査の対象外です。 値を持つセルには全て付いていました。判定はこれを読むようにし、v81 では読む手段が無かった 文字不一致を、経路A で 4 件、経路B で 4 件、新たに捕捉しています。

数量・単価にセルが付いた（v89）

items[].qty と items[].unit_price に座標が返るようになりました。 経路A で 475 件、経路B で 471 件。本編の測定時にはセルごと存在せず、箱も照合結果も無い状態で 値だけがありました。

短い数値に無理な箱を付けなくなった（v91）

1〜2 桁の数値セルが、長い数字の一部に箱を付けなくなり、代わりに nobox を返します。提供元の説明では、以前は ¥108 の「1」に数量の箱が付いて verified: true で返っていました。 少なくとも今回のサンプルでは、無理な箱付けが減ったと解釈できます。 ただし nobox の増加そのものは精度の指標ではないため、良し悪しの判断はここでは行いません。

03 こちらの実装を直した点

v82 で verified の意味が「文字照合の結果」から 「review に理由が立たなかったか」に変わりました。こちらの判定は verified=false を無条件に止める作りのままだったため、 nobox だけで false が立つ場合まで止めていました。 そのままでは、意図して通していたものまで止まり、素通し率だけが下がります。 理由の側を見て判断する形に変えています。

世代はレスポンスから自動で判別しています

呼び出し側にフラグを渡させる形にすると、渡し忘れたときに v82 以降のレスポンスを v81 の意味で判定して、静かに緩くなります。text_match を持つセルが 1 つでもあれば v82 以降、という判定で切り替えています。

この判別には限界があります

v82 以降なのに全ての値セルで text_match が欠けているレスポンスは、v81 と見分けが付かず v81 として扱われます。そのとき欠落は止められません。レスポンスの中だけでは識別できないため、 限界として引き受けています。

04 直っていないこと

同じ入力で結果が変わる

本編で「同じ条件で 2 回測って 95.4%」と書いた件です。変わっていません。 経路A・spec v3 で、同じ画像・同じ宣言を 2 回投げた結果です。

同一条件で 2 回投げた 20 枚の内訳
結果 枚数
完全に同じ 2 / 20
差がある 18 / 20
うち values そのものが違う 10 / 20

セル数も 85 から 87、87 から 86 のように動きます。1 回測って直った・直らないは判断できない、 という状況は本編から変わっていません。

素直に 2 回投げても測れません

こちらの冪等キーは「画像ハッシュ＋FieldSpec の指紋」から決定的に作っており、同じ条件なら 同じキーになるため、2 回目はそのまま同じレスポンスが返ります（1 回目 431 秒に対し 2 回目 31 秒、 20 枚とも完全一致）。キーに文字列を混ぜて、初めて実際に実行されました。 再測定の入口が未実装のため、提供元の助言に従いこの形で測っています。

near の位置判定（v85〜v87）

near は、値のそばに印字されているはずの語彙を宣言できる機能です。 v3_near 宣言での理由コードの出方が次のように変わりました。

v3_near 宣言での理由コード（件数）
理由コード v81 v91
ambiguous_occurrence 4 13
near_ambiguous — 1
text_mismatch 5 3
nobox 7 14

v85 で near_mismatch が分割された効果が出ています。「どの出現も満たさない」のか 「満たす出現はあるが別の場所にアンカーされた」のかが区別されるようになり、後者が ambiguous_occurrence として現れています。

v87 で明示された限界はそのまま残ります

OCR が「中野 / 様 / 邸」と語を分割した場合、「様」が単独の語になるため位置から判断できません。 効く条件と効かない条件が仕様に書かれたことで、こちら側で何を補うかを設計できるようになりました。

05 測定に使ったもの

呼び出しの内訳
タグ 条件 枚数
A_v91 経路A・spec v3 20
B_v91 経路B・spec v3 20
A_v91_r2 経路A・spec v3・冪等キーを変更（再現性） 20
A_v91_near 経路A・spec v3_near 20

計 80 回。ほかに冪等キーを変えずに投げた 20 回があり、これは同一レスポンスが返ったため 測定には使っていません。エンジンのバージョンは /health の 2 回目の応答で記録しています （初回はコールドスタートで engine が null になるため）。

数字は測定スクリプトから取っています。手で書き写していません。生レスポンスを添えた状態で、 次のコマンドで両方の数字が出ます。

python fixtures/measure.py --tags A_v91,B_v91 # この追補の数字

python fixtures/measure.py # 本編（v81 時点）の数字

同じ実データ・同じ判定で、レスポンスだけを入れ替えた比較です。 測定に使った生レスポンス 80 件は手元にあります。必要な方はご連絡ください。

本編のデモ、検証レポート、測定に使った生データは、依頼元が公開しています。 公開されている成果物 と 紹介いただいたプレスリリース をご覧ください。

公開されているレポートの数字は v81 時点のものです。現行の API で同じ測定をすると数字が一致しないため、 その差をこのページに残しています。
